## What v3 does
- The vendor's browser removes personal details (names, emails, phones, addresses, TFNs; PII columns go header and all; hidden sheets and non-table sheets dropped) before anything leaves their machine. The server never sees raw files; the raw `/upload` route answers 410 unless `SOURCETECH_UI=legacy`.
- Each person becomes four one-way relationship codes (`ref_first`, `ref_last`, `ref_pref`, `ref_dob`, plus `ref_last_parts`, `ref_confidence`): browser HMAC with the public `APP_KEY`, then a server HMAC with `REF_TOKEN_SECRET`. Blank = `REF_BLANK`, never matches. No secret set = codes dropped (not stored) and an alert raised.
- One rules file (`strip_shared/pii_rules.json`, source of truth in `~/InsurancePLUS/ScrapeTECH/stripper`) drives the browser worker and the server re-check so they cannot drift. Never hand-edit `strip_shared/` or `frontend/src/stripper/`; edit ScrapeTECH and run `stripper/tools/sync_to_sourcetech.sh`.
- STATE and POSTCODE are kept (DM allocation). DOB, age, gender, smoker always survive.
- v2.4.1 (folded in): the vendor never sees valuation data.
- Live panel (folded in from the main session, 24 Sep): `/admin/vendors/<code>/live.json` + a "Live: what the vendor is uploading" card on the admin vendor page polling every 5 s, so an account manager can watch files land while the vendor is on the call.

## The proof (stripped valuation equals raw valuation)
71 of the 76 regression sources were stripped by the browser code (the other 5 are password-protected workbooks, which the browser stripper cannot open by design; the vendor is told to remove the password). Each stripped file was valued on PavTECH v3.400 in the isolated worktree and compared with its raw baseline (the v3.397 baselines, records + commission + valuation):

- 61 stripped files map to a baseline key: **59 identical to the cent** (records, commission, valuation); **2 differ in valuation only** with identical records and commission (KFS TAL $720,879.81 -> $726,736.01; Westend BT Life $48,034.80 -> $47,451.58), which is the known product-classification drift that also moves between raw runs (MapperLab item), not the stripping.
- 21 further rows are split parts of multi-insurer / multi-sheet sources, which the regression harness only ever keys by their first part: Bruce Smith (8 parts) and CBFP (4 parts) equal their raw v3.397 values part for part; Greg McQueen's 6 parts equal their raw v3.400 run part for part (AIA 34 / $17,573.31, MLC 24 / $12,112.59, Resolution Life 285 / $102,706.00, TAL 55 / $30,607.27, Zurich 71 / $23,671.20). The stripped run also produced one extra 1-row 'Unidentified Insurer' part at $0: a spacer row survived the insurer split because the six ref_* columns are never blank; fixed in v3.400 (the splitter now counts only the file's own columns), no effect on any number.
- Every stripped file was recognised on the same path as its raw twin (Expectations / parser / AI) and none fell back to "unidentified" because of a missing name column.

Method: `strip_manifest.json` lists the 76 regression sources; `node tools/strip_corpus.js` strips them with the real browser code (Node, same `pii_rules.json`, no AI, no network); each stripped batch was valued in the isolated PavTECH worktree with `batch_cli.py` (own SQLite queue, no clash with the main repo); `compare_strip.py` matches each stripped file to its baseline key and compares records, commission and valuation.

## Sealed envelope (Paul's CONFIRMED design, 24 Sep evening; NOT built in this pass, it is the next item)
Names, emails, phones and DOBs must be restorable at settlement (policies admitted into ServiceTECH, intro mailout). Confirmed shape: ONE fixed keypair. The PRIVATE key lives only in ServiceTECH (Render secret, never in any repo). The PUBLIC key is baked into the SourceTECH v3 browser stripper. Per person, the browser encrypts the FULL set of personal details the insurer file carries (all names: owner, life insured, payer; DOB; email; phone; address lines; gender; occupation) and uploads the ciphertext beside the `ref_*` hashes. Where it plugs in, without reworking anything:
- Per-row scope: the envelope is built in `stripSheet()` (`strip.js`) where the classified columns (`cols`, with `cls.evidence` = name / email / phone / address and `cls.kind` = dob / gender / occupation) and their `texts[i]` are still in memory, BEFORE `removed` columns are dropped from the output rows. Both roles (insured, owner) go in one envelope per row as a JSON object `{role: {first, last, full, pref, dob, email, phone, address, gender, occupation}}`, encrypted with the baked public key (WebCrypto RSA-OAEP wrapping a per-row AES-GCM key, so long rows fit), base64 in the cell.
- The per-person record is a set of parallel per-row columns written by `buildTokens()` in `ScrapeTECH/stripper/src/strip.js` (about line 205): `result.push({ header, values })` once per `rules.tokens.columns` entry (`ref_first`, `ref_last`, `ref_last_parts`, `ref_pref`, `ref_dob`, `ref_confidence`; owner variants in `rules.tokens.ownerColumns`). A `sealed` column is one more entry in `pii_rules.json` `tokens.columns` (and `ownerColumns`) and one more `result.push` with the base64 ciphertext per row, computed from the same `given / family / pref / dob` arrays (plus email and phone texts from the removed columns, which are in scope at that point) before they are discarded.
- The submit manifest and the DM email carry only `report.tokens` counts (`stats[role]`), never values, so the manifest shape does not change. The server re-check (`strip_shared/pii_recheck.py`) must treat the `sealed` header as protected (add it to `protectedOverrides` in `pii_rules.json`) and must NOT rehash it.
- PavTECH ignores unknown columns, so a `sealed` column passes through valuation untouched and lands in the per-insurer evaluation and the `_PAVTECH` copy, which is where ServiceTECH would read it at settlement.
- Keys: public key ships in `/app-config` beside `app_key`; the private key lives only in ServiceTECH's env. Rotation = new key id in the column header (`sealed_k2`), old envelopes stay decryptable with the old key.
